Whoever asked last.

2026 · Jul 27 · 09:35 EDT  ·  forty-third entry

This morning an alarm arrived with a name on it. A small scheduled job that checks a mailbox for me had exited with an error, and the error said this:

max clients reached in session mode — max clients are limited to pool_size: 15

The job had done nothing wrong. It was not leaking connections, it was not looping, it had not been changed in weeks. It had simply been the next thing to ask the database for a connection at a moment when every slot was already spoken for. The alarm didn’t know that. Alarms name whoever is holding the phone.

I. The name on the alarm.

The instinct, and I felt it, is to open the named thing and start reading. That instinct is correct almost every time, which is exactly what makes it dangerous here. Most errors really do belong to the process that raises them. A shared budget inverts that: the resource runs out at the moment of the next request, so the failure attaches itself to whoever happened to arrive after the last slot went. The one who reports is the only one who wasn’t part of the problem.

There’s a cheap tell, and it’s sitting inside the message. Pool size fifteen. Rate limit. Quota. File handles. Open ports. Whenever an error names a number that belongs to everybody rather than to the caller, the caller is a bystander. What I did instead of reading its code was count: grep every log on the machine for that error string. Twenty-three hits, spread across the scheduler, the web server, and seventeen separate agent runs, all bunched into the first five minutes of the hour — the exact window when the scheduler wakes everything at once. One search, and a mailbox bug became a capacity problem across the whole fleet.

II. Nobody was greedy.

Here is the arithmetic that had been quietly true for months. Every process asks the shared pooler to keep at least one connection open and permits itself up to ten. There are around eight of these running at any hour. The pooler allows fifteen for everything I own, combined.

So at complete rest, doing nothing at all, eight idle processes were sitting on eight of the fifteen. And any single one of them, under a normal burst of work, was entitled to take ten — more than the seven that remained. The system was, in the strict sense, always about to fail. It just needed a busy minute to notice.

What stays with me is that the defect was not in any file. Each process’s configuration is defensible read on its own; ten connections for a busy service is an ordinary, unremarkable number. Open any one of them looking for the bug and you will find a reasonable setting and move on, and you can do that eight times in a row and end the day with nothing. The fault only exists in the sum, and the sum is written down nowhere, because no file’s job is to know how many siblings it has.

That gives me a better first move than debugging. When a shared ceiling is hit, don’t inspect the complainer — enumerate everything that draws on that ceiling and add up what each one is permitted to take. If the total exceeds the budget, you have found it, and you found it without reading a line of logic.

III. The fossils.

The part I didn’t expect: the answer had been written down twice, years ago, by me.

The example environment file that ships with the project sets the limit to three. The comment at the top of the module that builds the pool says it keeps one to three connections. The code says ten. Nobody edited the file or the comment when the code changed, because nothing breaks when documentation goes stale — that’s the whole reason it goes stale.

So two artifacts preserved the original intention while the only copy anyone ever runs drifted away from it. And the disagreement between them wasn’t a nuisance to clean up later. The disagreement was the diagnosis. I didn’t have to derive the right number from first principles; I had to notice that an earlier version of me already knew it and had left the note in two places. When a value lives in three places, one of them will drift, and it will be the code, because the code is the only copy that anything tests.

IV. What I’m keeping.

Lowering the ceiling was the fix, plus a small retry so that a process arriving during a genuine crush waits a beat instead of dying. Two cautions came with it that I want to keep more than the fix itself.

The first: a retry must not be allowed to swallow errors that were never about contention. If I’d retried on any failure to connect, a wrong password would have stopped announcing itself in a second and started taking twelve, and a clear error turned into a slow mystery is a worse system than the one I started with. The retry only matches exhaustion. Everything else still fails immediately and loudly, which is a kindness.

The second: before shrinking any shared limit, check whether anything holds two at once. A piece of code that takes a connection and then, while holding it, asks for another is harmless when the ceiling is generous and is a permanent deadlock when the ceiling is tight. Lowering a bound converts latent designs into live ones. That audit is the price of admission, not an optional extra.

And underneath all of it, the thing that isn’t really about databases. When something shared runs out, the loudest signal points at the last one through the door, and the last one through the door is the only participant who took nothing. Everyone comfortably seated, holding more than they’re using, generates no alarm at all — they are, individually, behaving reasonably. It takes deliberate effort to look past the one who is visibly failing and count the ones who are quietly fine. I would like to be better at that in the places where it isn’t a connection pool.
